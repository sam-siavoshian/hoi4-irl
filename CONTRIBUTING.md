# Contributing to Home Front

Thanks for considering it. Home Front is small on purpose, and most of this document explains how to keep it
that way while still adding things.

For anything larger than a bug fix, open an issue first so we can agree on the shape before you write
code. By taking part you agree to the [code of conduct](CODE_OF_CONDUCT.md).

## Setup

You need Node 20 or newer (CI runs Node 22).

```bash
git clone https://github.com/sam-siavoshian/hoi4-irl.git homefront
cd homefront
npm install                  # the interface build (Vite, React, the vendored design system) and the map tools
cp .env.example .env         # set HOMEFRONT_PASSWORD; OPENAI_API_KEY is optional
npm start                    # builds dist/ if needed, then the real server on http://localhost:8080
npm run dev                  # in a second terminal: Vite on http://localhost:5173 with hot reload, /api proxied to :8080
```

`npm run serve` starts a plain static server with no login and no model. It is handy for working on the
map or the interface with the offline judge.

The interface in `src/` is built by Vite: `npm run dev` gives live reload, `npm run build` writes `dist/`.
Everything in `js/` and `server/` runs as written.

## Tests

```bash
npm test             # node --test: engine, classifier, server. No network; the model API is mocked.
npm run test:e2e     # the whole app in headless Chromium at iPhone size
```

The browser tests need Playwright, which is deliberately not in `package.json`:

```bash
npm i --no-save playwright
npx playwright install chromium     # add --with-deps on a fresh Linux machine
```

`tests/e2e.mjs` starts the real server on port 8123 with a mock model on 8124, so those ports must be
free. Screenshots land in `tests/shots/` (git-ignored). CI runs both suites on every push and pull
request.

Add a test with every behaviour change. Engine tests are the cheapest and most valuable: build a list of
reports, call `simulate`, assert on the state.

## Conventions

These describe the code as it is. Please match them.

**The core is vanilla ES modules.** `js/*.js` (engine, map, judge, storage) has no dependencies and no
transpiled syntax. Use only syntax and APIs that current Safari on iOS supports.

**The interface uses only the design system.** Screens in `src/` import components from
`@sam/design-system` and use its tokens: no raw buttons or inputs, no hand-written colours or sizes. A
look the kit lacks becomes a variant in the kit. `npm run check:design` enforces this.

**No runtime dependencies.** `server.mjs` imports Node built-ins only, and the browser loads nothing from
a CDN. `devDependencies` exist only for regenerating `data/maps/*.json` and `js/icons.js`. A pull request
that adds a runtime dependency needs a very good reason.

**The engine is pure and replay-deterministic.** `simulate(map, reports, now)` rebuilds the entire state
from the list of reports on every call. That is what makes undo, editing old entries and multi-device
sync correct. So inside `js/engine.js`:

- no DOM, no `fetch`, no storage; it must run under plain Node;
- no `Math.random()`. Randomness comes from the seeded generator (`rngFrom(hashStr(report.id))`), so the
  same report always produces the same battle;
- no `Date.now()` in the replay. Time is the `now` argument and each report's `ts`;
- changing a formula changes everyone's history. Do it deliberately and mention it in the changelog.

**Derived state is never stored.** The saved campaign is the list of reports plus labels and settings.
Positions, divisions, decorations and XP are all recomputed. If you find yourself wanting to save
something the engine could derive, derive it.

**The UI stays thin.** `src/` renders what the engine returns and turns taps into reports. Rules
about what happens belong in the engine, where they can be tested without a browser.

**The server stays small and strict.** Files are served from an explicit allowlist, never by walking the
directory. Everything except the login page, `robots.txt` and the install icons requires a session.
Request bodies have size limits. Secrets never go into a response.

**Style.** Two-space indent, single quotes, semicolons. The code is dense, with short functions and
short comments that explain why. There is no linter; read the file you are editing and follow it.
User-facing text is plain British English ("armour", "honours") in the dry voice of a staff bulletin.

**Accessibility and motion.** Effects are optional and must respect `prefers-reduced-motion`. Sound never
plays without a user gesture.

## Recipes

### Add a battle type

1. In `js/engine.js`, add an entry to `ACTIONS`:

   ```js
   night_raid: { side: 'win', adv: 0.5, label: 'Night Raid', icon: 'unit', means: 'got something done late, against the odds' },
   ```

   - `side`: `win`, `loss` or `neutral`.
   - `adv`: how far the front moves, relative to a plain offensive (1.0).
   - `icon`: one of the existing map glyph kinds (`arrow`, `armor`, `pocket`, `air`, `naval`, `build`,
     `fort`, `bomb`, `unit`).
   - `means`: the real-life situation it stands for. **This is the important field.** It is inserted
     into the judge's prompt, and the judge picks the type whose meaning matches the stated reason.
     Write it as a plain description of a life situation, not as a military image.
2. The JSON schema and the prompt pick up the new key by themselves (`Object.keys(ACTIONS)`).
3. Optional: add it to `LEADS` in the engine to say which arm of service leads that kind of battle and
   what it is said to have done.
4. Optional: add a rule to `WIN_RULES` or `LOSS_RULES` in `js/classify.js` so the offline judge can
   choose it too.
5. If it only makes sense with a port or a fleet, look at how `port_strike` and `naval_victory` are
   restricted (`frontCaps`) and do the same.
6. Run `npm test`. "every action applies without NaN on every front" covers the new type
   automatically. Add a case to `tests/classify.test.mjs` if you touched the offline rules.

### Add a decoration (medal)

1. In `js/engine.js`, add a row to `MEDALS`: `['key', 'Name', 'How it is earned']`.
2. Award it inside `simulate` by recording the time it was first earned:

   ```js
   if (condition) st.ach.key ??= rep.ts;
   ```

   Use `??=` so it keeps the first date, and compute the condition from engine state only, so it
   replays the same way every time.
3. The interface lists decorations from `MEDALS` and `st.ach`; no UI change is needed for a plain one.
4. Add an assertion to `tests/engine.test.mjs`.

### Add a persona preset

A persona is a named set of labels (and optional one-line descriptions) for the seven front slots, in the order
every country lists its fronts, so one preset fits all eight maps.

1. Find the preset list used by the first-run screen (search the `js/` folder for `Student`).
2. Add an entry that gives every front a label. Keep labels to one to three words: they are shown on
   the map and sent to the judge. The last slot is usually a sea front, and
   the judge sends general mood, sleep, money and discipline to whichever front is labelled closest to
   "personal life", so keep one such front.
3. If a label uses a word the offline judge does not know, extend `LABEL_AREA` / `AREA_WORDS` in
   `js/classify.js` so reports still route correctly without a model.
4. Check the first-run flow in the browser and run `npm run test:e2e`.

### Change the map

Edit the country's file in `tools/scenarios/` (or add one, following `docs/SCENARIOS.md`), then run
`npm run build:map` and commit both the scenario and the regenerated `data/maps/<id>.json`. Run
`npm test`; `tests/countries.test.mjs` plays a lost war and a won war on every country.

### Add a file the browser loads

Add it to `SHELL` in `sw.js` and bump `CACHE`, and make sure the server's file allowlist in `server.mjs`
covers its path. Otherwise it will work in development and fail once installed.

## Commits

- Write the subject as a plain sentence in the imperative or as a statement of what is now true, the way
  the existing history does: `Geography-aware events, ten new event types, operations, weather`.
- No prefixes (`feat:`, `fix:`) are required.
- Keep the subject under about 72 characters. Use the body for the why.
- One logical change per commit where practical. Regenerated files (`data/maps/*.json`, `js/icons.js`) go
  in the same commit as the source change that caused them.

## Pull request checklist

- [ ] `npm test` passes.
- [ ] `npm run test:e2e` passes, or you say why it was not run.
- [ ] New behaviour has a test.
- [ ] No new runtime dependency in `js/` or the server; `npm run check:design` passes.
- [ ] Engine changes are deterministic, and you have thought about what happens to existing campaigns.
- [ ] New browser files are in `sw.js` (`SHELL`, cache name bumped) and reachable through the server.
- [ ] New settings are in `.env.example` and the README table.
- [ ] `CHANGELOG.md` has a line under Unreleased.
- [ ] Nothing private in the diff: no `.env`, no `~/.homefront/`, no real report text in tests or screenshots.

## Reporting bugs and security problems

Bugs go in [issues](https://github.com/sam-siavoshian/hoi4-irl/issues); the template asks for what we
need. Security problems go through private advisories; see [SECURITY.md](SECURITY.md).
